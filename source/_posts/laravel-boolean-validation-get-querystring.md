## 一个看起来很诡异的现象

后台有个列表页，支持按「是否启用」筛选，对应一个布尔字段 `is_active`。需求很普通：勾上「是」就只看启用的，勾上「否」就只看停用的。

前端把这个条件发给后端，结果列表接口直接报错：

```json
{
  "status": "error",
  "message": "参数错误 (is_active)"
}
```

诡异的地方在于：**同样一份数据，走下载导出接口（POST）一切正常，走列表查询接口（GET）就必报错。**

代码是同一套校验规则，数据是同一个勾选框出来的，凭什么换个请求方法结果就不一样？

这篇就把这个坑从头到尾捋一遍。结论先放这里：

> **GET 的 query string 只能携带字符串**，布尔 `true` 会被序列化成字符串 `"true"`；而 **Laravel 的 `boolean` 校验规则用的是严格比较，白名单里压根没有字符串 `"true"`**。两件事一撞，就报参数错误。

## 第一块拼图：Laravel 的 `boolean` 规则到底认什么

很多人以为 `boolean` 校验规则是「只要长得像布尔就行」，其实不是。翻一下框架源码（`ValidatesAttributes` 里的 `validateBoolean`）：

```php
public function validateBoolean($attribute, $value)
{
    $acceptable = [true, false, 0, 1, '0', '1'];

    return in_array($value, $acceptable, true);  // 第三个参数 true = 严格比较
}
```

关键在 `in_array` 的第三个参数 `true`，它开启了**严格比较**（既比值也比类型）。所以白名单实际上只有这六个东西：

- 真布尔 `true` / `false`
- 整数 `0` / `1`
- 字符串 `'0'` / `'1'`

注意：**字符串 `"true"` 和 `"false"` 不在里面。**

我本地挨个试了一遍，结果一目了然：

| 传进去的值 | 类型 | `boolean` 规则 |
| --- | --- | --- |
| `"true"` | string | ❌ FAIL |
| `"false"` | string | ❌ FAIL |
| `"1"` / `"0"` | string | ✅ PASS |
| `true` / `false` | bool | ✅ PASS |
| `1` / `0` | int | ✅ PASS |

也就是说，只要到达校验那一刻的值是字符串 `"true"`，无论你前端本意多么「布尔」，都会被一票否决。

## 第二块拼图：GET 请求是怎么把布尔变成字符串 `"true"` 的

前端那边，本意其实是发真布尔的。代码大致长这样：

```javascript
// 勾选框的值是 '1'/'0'，这里转成布尔数组想发给后端
payload.is_active = source.isActive.map(v => v === '1')   // 产出 [true, false]
```

到这里都没问题，`payload.is_active` 是货真价实的 `[true, false]`。

问题出在请求库（这里是 axios）发 GET 请求的那一步。GET 没有请求体，所有参数都得拼进 URL 的 query string，而 **URL 里只有字符串这一种数据类型**。于是 axios 在序列化时，把布尔 `true` 直接 `toString()` 成了字符串 `"true"`：

```text
GET .../list?is_active[0]=true&is_active[1]=false
                          ^^^^             ^^^^^
                       已经是字符串了，不再是布尔
```

请求到了后端，PHP 从 query string 里解析出来的就是字符串 `"true"`。中间就算有做 urldecode 之类的处理，`"true"` 里没有需要解码的字符，原样放过。最后送进 `boolean` 校验——字符串 `"true"` 不在白名单——`FAIL`。

整条链路串起来就是：

```text
前端真布尔 true
   → axios GET 序列化进 URL
   → 变成字符串 "true"
   → 后端解析出 "true"（字符串）
   → boolean 规则严格比较
   → 白名单没有 "true"
   → 参数错误 💥
```

## 那为什么 POST 就没事？

同样的数据走下载导出接口（POST）却完全正常，因为 **POST 把参数放在请求体里，用 JSON 编码，而 JSON 是有布尔类型的**：

```text
Content-Type: application/json
body: {"is_active": [true, false]}     // 真·JSON 布尔，不是字符串
```

后端用 `json_decode` 解出来，`true` 依然是 PHP 的真布尔 `true`，正好命中白名单，校验通过。

一张表对比就很清楚了：

| 接口 | 方法 | 到达后端时 `is_active` 的形态 | `boolean` 校验 | 结果 |
| --- | --- | --- | --- | --- |
| 列表查询 | GET | 字符串 `"true"`（query string 序列化） | ❌ FAIL | 报错 |
| 下载导出 | POST | 真布尔 `true`（JSON body） | ✅ PASS | 正常 |

**同一套校验规则，结果天差地别，根子在「参数靠什么载体传输」。** 这也是为什么很多人第一反应「校验规则没动过啊」，然后卡很久——因为 bug 根本不在校验规则本身。

## 怎么修：三个方案和各自的坑

### 方案 A：放宽后端校验，让它也接受 `"true"`

最直觉的做法：把 `boolean` 换成自定义规则，额外接受字符串 `"true"/"false"`。

**但这个方案有个隐藏的大坑**：如果你的后端拿到参数后，还会**再转发给下游服务**（比如网关层把请求转给真正的数据服务），那么下游往往还有一道**同样的** `boolean` 校验。你在入口放宽了，字符串 `"true"` 原样透传过去，下游照样拒——**错误只是从你眼前挪到了下游，没真正解决。**

> 教训：**多层服务架构里，只修一层等于没修。** 一定要顺着参数的完整流向，确认每一道关卡都能过。

### 方案 B：后端把值转成真布尔

在入口接收后，主动把元素规整成真布尔再往下走：

```php
$value = filter_var($input, FILTER_VALIDATE_BOOLEAN);  // "true"/"1"/1 → true
```

好处是**契约最健壮**：不管调用方传 `"true"`、`"1"` 还是真布尔，后端都兜得住。如果后端再用 `http_build_query` 往下游转发，真布尔会被序列化成 `"1"/"0"`，正好又能过下游那道 `boolean` 校验。端到端通畅。

代价是后端要多写一层转换，并且要想清楚 nullable / 空值的边界。

### 方案 C：前端直接传 `"1"` / `"0"`（最终采用）

既然 `boolean` 规则认字符串 `"1"/"0"`，那前端干脆别转布尔了，直接把勾选框的值（本来就是 `'1'/'0'`）原样发出去：

```javascript
// 改前：转成布尔 → GET 时被序列化成 "true" → 校验 FAIL
payload.is_active = source.isActive.map(v => v === '1')

// 改后：直接传 '1'/'0' → 不管 GET 还是 POST 都能过 boolean 规则
payload.is_active = source.isActive
```

- GET：query 里是 `is_active[0]=1`，字符串 `"1"` ✅
- POST：body 里是 `{"is_active": ["1"]}`，字符串 `"1"` 同样 ✅

一处改动，GET 和 POST 都搞定，改动面最小，所以这次选了它。

**但要留个心眼**：方案 C 是前端单边修复，**后端的契约其实没变**——它依然只认 `1/0/真布尔`、依然拒字符串 `"true"`。这意味着：

- 任何其他调用方（Postman、curl、以后别的前端）只要按「布尔字段」的直觉传 `"true"`，照样会踩同一个坑；
- 如果接口文档里写的示例是 `Example: true`，就和「实际要传 1/0」对不上，产生**文档漂移**，建议顺手把文档示例也改成 `Example: 1`。

如果想让后端对「真布尔 / 字符串 / 1/0」全都健壮，那还是得用方案 B。**方案 C 省事，方案 B 治本，按场景选。**

## 顺手验证的一个点：数据库这关稳不稳？

修完还担心一个问题：传给数据库做 `WHERE is_active IN (...)` 时，`"1"/"0"` 这种字符串能正确匹配到布尔列吗？

实测下来，主流数据库的 `boolean` 列对 `"1"/"0"` 和 `"true"/"false"` 这两种字符串绑定参数都能正确命中对应的行——**数据层不是约束，约束全在应用层的校验规则上。** 所以放心，瓶颈不在 SQL。

## 经验总结

把这次的坑沉淀成几条可复用的 takeaway：

1. **`boolean` 校验规则是严格比较，只认 `true/false/1/0/'1'/'0'`，不认字符串 `"true"/"false"`。** 这是最反直觉的一点，记牢。

2. **GET 和 POST 不是「换个方法」那么简单**：GET 的 query string 只能传字符串，布尔/数字都会被 stringify；POST 的 JSON body 保留原生类型。涉及布尔、数字、null 的参数，换请求方法就可能换行为。

3. **遇到「同样的代码不同结果」，别盯着校验规则死磕，先看参数到达那一刻到底变成了什么类型。** 在校验前 `dd($value, gettype($value))` 一下，往往一秒破案。

4. **多层服务转发时，只修入口那一层是假修复**，错误会被推到下游。修复前先把参数的完整流向画出来，确认每道关卡都能过。

5. **前端绕过 vs 后端兜底是两种修复哲学**：前端改传值省事但契约没变、留隐患；后端转真布尔治本但要多写代码。看这个接口未来还有多少调用方来决定。

说到底，这个 bug 的「诡异」全是错觉——只要把「传输载体决定数据类型」和「校验规则用严格比较」这两件事摆到一起，一切都顺理成章。
